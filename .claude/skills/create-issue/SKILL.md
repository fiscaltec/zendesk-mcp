# Create an issue

Use this when someone asks to create, raise, log or file an issue, or when work turns up that
`CLAUDE.md` says should be tracked as one. It encodes what raising #2–#10 by hand had to rediscover,
and was ported from `searledan/spendy`'s skill of the same name (#11), then adapted to this
repository's labels, forms and writing rules.

**Read `CLAUDE.md` → *GitHub issues (issue-driven work)* first.** This skill is the procedure; that
section is the standard, and where they disagree it wins — fix this file to match.

Hard rules, each learnt the hard way:

- **REST only — `gh api`, never `gh issue …`.** `gh issue create/edit/view` are GraphQL underneath and
  fail in a cloud session with `HTTP 403: GitHub GraphQL is not available from Claude Code sessions`.
  `gh api` works in both cloud and local sessions. (The GitHub MCP connector also works in the cloud,
  but `CLAUDE.md` standardises on `gh`.)
- **Never put customer data in an issue** — no ticket, user or organisation content, names, email
  addresses, subjects or comment text. Issues are visible to everyone with repository access and
  outlive the data. Describe *shapes* ("a ticket whose `via.channel` is `api` and has no
  requester"), and refer to Zendesk records by id only when the id itself is needed.
- **Evidence, not assertion.** Quote the real error output, cite file paths and line numbers, and say
  what was *verified* versus *assumed*. Check every count, name and line number against the source
  before posting — drafts of #2–#9 had a wrong marker count and wrong test class names until
  checked.
- **UK English** throughout ("behaviour", "organisation", "authorise").
- **End the body with the attribution footer** that issues and issue comments from Claude Code carry
  here (pull-request descriptions carry a different one):

  ```markdown

  ---
  _Generated by [Claude Code](https://claude.ai/code)_
  ```

`{owner}/{repo}` in the commands below is `gh`'s own placeholder, filled from the checkout's `origin`
remote; it needs no quoting and works as written from inside this repository.

## Step 0 — Gather what the issue needs

Settle these before drafting. Ask the person only for what you cannot establish yourself.

1. **Type** — exactly one label. Each type has a form under `.github/ISSUE_TEMPLATE/` whose title
   prefix and sections the issue follows (`ux` has no form):

   | Type label | When | Form | Title prefix |
   |---|---|---|---|
   | `feature` | a new tool or capability | `feature.yml` | `feat:` |
   | `bug` | something does not work as documented | `bug.yml` | `fix:` |
   | `tech-debt` | refactoring, upgrades, test gaps, tooling, clean-up | `tech-debt.yml` | `chore:` (or `refactor:`) |
   | `security` | hardening, a vulnerability, a compliance gap | `security.yml` | `fix:` |
   | `ops` | Azure, deployment, configuration, Entra | `ops.yml` | `chore:` (or `ci:`) |
   | `documentation` | prose for **humans**: `CLAUDE.md`, `README.md`, `ACCESS.md`, `docs/` | `documentation.yml` | `docs:` |
   | `content` | copy an **LLM** reads: tool `[Description]` and `Title` values, `ZendeskServerInstructions.Text` | `content.yml` | `docs:` |
   | `ux` | the experience of a person using the server (sign-in, connect pages, error wording they see) | none — use the tech-debt sections | `feat:` or `fix:` |

   The prefix is a Conventional-Commits type and becomes the branch prefix (`CLAUDE.md` →
   *Lifecycle* step 3). `content` is not cosmetic: wording changes which tool a model picks and how
   it calls it, so a content issue must state the **observed effect** on model behaviour.

2. **Priority** — **assess it yourself** from impact, urgency and its place among the other open
   issues; do not ask the person to choose. Say why in one line when you present the draft.

   | Label | Means |
   |---|---|
   | `priority: high` | wrong behaviour in production, a security exposure, or it blocks other work |
   | `priority: medium` | matters, but nothing is broken while it waits |
   | `priority: low` | nice to have, no time pressure |

3. **Summary** — what is wrong or missing, and why it matters. Enough to write the title and lead
   paragraph.

4. **Related issues** — gather them now, so the draft cites them as `#N` instead of having
   cross-references patched in afterwards (which is what happened to #2–#9):

   ```bash
   gh api --paginate 'repos/{owner}/{repo}/issues?state=open&per_page=100' \
     --jq '.[] | select(.pull_request | not) | "#\(.number) [\([.labels[].name] | join(", "))] \(.title)"'
   ```

   Issues learnt from in the sibling repository are written `vitally-mcp#NNN` (`CLAUDE.md` →
   *Provenance*).

## Step 1 — Check for duplicates

Search titles **and** bodies of open and closed issues, with two or three alternative keywords:

```bash
gh api --paginate 'repos/{owner}/{repo}/issues?state=all&per_page=100' \
  --jq '.[] | select(.pull_request | not)
        | select((.title + " " + (.body // "")) | test("<keyword>|<synonym>|<other>"; "i"))
        | "\(.state) #\(.number) \(.title)"'
```

This lists and filters rather than calling the search API, so the match is exact over whole titles
and bodies and depends on no search index. (Unlike in spendy, where the skill says the search API is
refused, `gh api -X GET search/issues -f q='repo:{owner}/{repo} is:issue <keyword>'` works in this
repository's cloud sessions — checked 2026-11-04 — but only with `is:issue` in `q`; without it GitHub
answers `HTTP 422: Query must include 'is:issue' or 'is:pull-request'`.)

If something similar exists, show it to the person and ask whether to proceed, cite it, or update
it instead. A closed issue that covered the same ground is a `## Dependencies` entry at least.

## Step 2 — Draft

Take the sections from the matching form, so the issue and the form cannot drift apart. Each form
field's `label:` becomes a `##` heading, in the form's order:

```bash
sed -n 's/^ *label: *//p' .github/ISSUE_TEMPLATE/<type label>.yml   # for ux, use tech-debt.yml
```

Then apply `CLAUDE.md` → *Writing issues* over the top:

- **Title** — the Step 0 table's *Title prefix* (`chore:`, not the label `tech-debt:`), then the scope at a glance:
  `fix: Update_ticket drops tag changes when tags are passed with other fields`.
- **Lead paragraph** before the first heading — what and why, and how it was discovered if that
  matters. Someone reading only this paragraph should know whether the issue is theirs.
- **The problem section** (`## Problem`, or the form's equivalent: *What happened?*, *Motivation*,
  *Description*, *What is wrong or missing*, *What & where*) carries the evidence: real error output
  in a code block, `path/to/File.cs:123` references, and an explicit verified-versus-assumed split.
- **The fix section** (`## Proposed fix` or the form's equivalent) gives concrete numbered steps and
  lists **rejected alternatives with the reason**, so the next session does not re-litigate them.
- **`## Files to create/modify`** — explicit paths.
- **`## CLAUDE.md updates needed`** — which sections of `CLAUDE.md` the change invalidates. The most
  common source of drift; add it even where the form lacks it (`content`, `documentation`) if any
  section would become untrue.
- **`## Dependencies` last** — `#N` with the relationship ("blocked on #N", "related to #N",
  "follows vitally-mcp#NNN"), or "None".
- Prefer **tables** for structured data and **code blocks** for commands; flag anything
  designed-but-unvalidated as such.
- Drop a form section that genuinely does not apply rather than writing "N/A" under it; keep the ones
  marked required in the form.

**Write it for a fresh session.** Each issue is normally picked up by a new session, often a subagent
in a worktree, whose only context is the issue body and `CLAUDE.md`. Nothing may depend on this
conversation: name the files, quote the evidence, state the decisions already made.

Show the draft — title, labels with the one-line priority reason, and body — and wait for the
person's go-ahead before creating it, unless they have said to go ahead without asking.

## Step 3 — Create

Write the body to a file in the scratchpad (never inline: quoting breaks on backticks and `$`), then:

```bash
gh api 'repos/{owner}/{repo}/issues' \
  -f title='<prefix>: <title>' \
  -F body=@<body-file> \
  -f 'labels[]=<type label>' \
  -f 'labels[]=priority: <high|medium|low>' \
  -f 'labels[]=status: ready' \
  --jq '"#\(.number) \(.html_url)"'
```

`-F body=@file` reads the file; `-f` would post the literal string `@file`. Use `-f` for the title
and labels so a title starting with `@` or a digit is not reinterpreted.

**Labels:** exactly one type, one `priority:` and one `status:` label. Use `status: ready` if the issue
is defined enough to start and nothing blocks it; `status: blocked` if it waits on another issue or a
person — then add a comment saying exactly what it waits for. Every label must already exist:
**a label GitHub does not know is silently created**, so check a spelling you are unsure of with
`gh api 'repos/{owner}/{repo}/labels/<url-encoded name>'` first. Do not assign anyone at creation;
assignment follows the status (`CLAUDE.md` → *Lifecycle*).

## Step 4 — Verify

Read it back rather than trusting the create call:

```bash
gh api 'repos/{owner}/{repo}/issues/<number>' --jq '{title, labels: [.labels[].name], assignees: [.assignees[].login], body}'
```

Confirm:

- the title carries the right prefix;
- exactly one type, one priority and one status label, all spelt as `CLAUDE.md` → *Labels* lists;
- every section from Step 2 is present, `## Dependencies` last, and the footer at the end;
- every `#N` resolves to the issue you meant, and every file path and line number you cited exists;
- no customer data slipped in.

Fix anything wrong with `gh api -X PATCH 'repos/{owner}/{repo}/issues/<number>' -F body=@<file>`
(or `-f title=…`), then report the number and URL to the person.

## Afterwards — moving the issue through its lifecycle

Status changes go through `.claude/scripts/issue-status.sh`, which works over REST, adds the new
label before removing the old one, refuses a label the repository lacks, assigns the owner while the
issue is `in-progress` and unassigns otherwise, and reads the result back:

```bash
bash .claude/scripts/issue-status.sh <number> in-progress   # starting work: assigns searledan
bash .claude/scripts/issue-status.sh <number> blocked       # stalled: unassigns; comment what blocks it
bash .claude/scripts/issue-status.sh <number> complete      # after the squash merge: unassigns
```

The full lifecycle is `CLAUDE.md` → *Lifecycle*.
